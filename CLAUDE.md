# Plop

Personal side project: a daily word ladder from a four-letter start word to POOP, deployed as a
static page on GitHub Pages. Treat it as a standalone hobby repo: the Crusoe platform context in the user-level CLAUDE.md is
irrelevant here. Commits use the repo-local identity already configured
(`thenickberry@users.noreply.github.com`).

## Layout and the one rule

- `src/game/` is pure logic with no DOM: ladder validation and BFS, daily scheduling, share text,
  stats, storage. Every module here has a test in `tests/`.
- `src/ui/` is DOM only: board, keyboard, dialogs, toast.
- `src/main.ts` is the controller wiring the two together.

Keep new logic in `src/game/` with a test. If a change to `main.ts` grows a branch worth reasoning
about, it belongs in `src/game/`.

## Settled decisions

Chosen deliberately in a design review. Build on them as fixed points.

- The game is called Plop. poople.io is a real company; credit it as inspiration only.
- Deliberate divergences from the original: reused words are rejected, a give-up button exists and
  breaks the streak, and the accepted list is wide (ENABLE1) because the original's narrow list
  draws complaints.
- Puzzles roll over at **midnight UTC**, not local midnight, so friends in different timezones
  share a puzzle number. Puzzle #1 is 2026-09-24. Both live in `src/game/daily.ts`.
- Tiles have two states only: brown for a positional match, neutral otherwise. No "present but
  misplaced" colour.
- Deferred on purpose: practice mode, hints, theme toggle, PWA, custom domain, accounts.

## The word schedule is load-bearing

`src/data/words.json` is generated by `scripts/build-words.mjs` and committed. The daily schedule is
`scripts/pinned.txt` verbatim, followed by a seeded shuffle of the start pool. **Any change to the
inputs reshuffles every unpinned puzzle**: editing `scripts/exclude.txt` or `scripts/no-start.txt`,
bumping a source list, or touching the par bounds or difficulty filter. So before regenerating,
append every released puzzle word to `pinned.txt` in order (a test asserts the schedule starts with
it). Adding words to `exclude.txt` also removes them from accepted moves, which can lengthen or sever
existing ladders, including pinned ones, so rerun the tests, which assert every scheduled par
against the shipped dictionary. To keep a word as a move but never as a start word, use
`no-start.txt` instead.

The difficulty filter keeps a start word only if one of its shortest ladders uses familiar words
alone (the OpenSubtitles 50k frequency list). It exists because FUJI, briefly puzzle #2, has a single
legal move, FUCI. FUJI was swapped for WAVE on its own day; a pinned word can be swapped like that
because `loadGame` drops a save whose start word no longer matches the puzzle, but players who had
already finished keep that day's stats.

The generator reads `scripts/.cache/{enable1,common,blocklist,familiar}.txt` before fetching. Node's
fetch cannot reach GitHub from the Claude Code sandbox; fill the cache with curl first, using the
URLs in `SOURCES`.

## Gotchas

- Build and preview must agree on the base path. GitHub Pages serves from `/plop/`, so CI sets
  `VITE_BASE=/plop/`. A `vite preview` started without it serves assets at the root and the page
  loads blank with 404s in the console. Renaming the repo means changing `SITE_URL` in
  `src/game/share.ts` too; CI derives the base from the repo name.
- `npm install` in the sandbox needs `--cache ~/.cache/npm`; the default cache dir is read-only there.
- Test fixtures: POOP has an O in position 2 and a P in positions 1 and 4, so innocuous-looking
  words like COLD already score a brown tile. Use CAKE-style words when a fixture needs zero matches.
- The board reuses row elements so only the newly submitted row plays the flip animation.
  Rebuilding all rows on render would re-animate the whole board.
- The physical keyboard listener ignores keys while any `<dialog>` is open, so typing into a future
  dialog input will need that guard relaxed.
- `recordOutcome` is idempotent per puzzle number. Stats never double-count a reload.

## Verifying UI changes

Unit tests do not touch the DOM. After a UI change, run `npm run build` with `VITE_BASE=/plop/`,
start `vite preview` with the same variable, and drive it with the Playwright MCP tools at a 420px
viewport in both colour schemes. The flows the smoke pass covers: first-visit help dialog,
the four rejection toasts, keyboard input from both physical keys and on-screen buttons, results
dialog after a win and after give-up, share text on the clipboard, stats dialog, and a reload
restoring a finished game with results reopened. Deploying without that pass is guessing.
